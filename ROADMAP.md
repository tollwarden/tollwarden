## 0. API-key rotation & revocation — ✅ BUILT 2026-07-16

The oldest open security gap is closed. The account (KeyRecord) is the
identity; the `psk_` secret is a credential pointing at it. `POST
/v1/keys/rotate` (authed by the current key) mints a replacement secret bound
to the SAME account — usage, remaining free calls, plan, and dashboard stats
carry over; rotation never resets the free tier so it can't be farmed. The old
secret honors a grace window (`grace_seconds` default 900, 0 = instant death,
max 24 h) during which it can scan but NOT rotate/revoke — a leaked old secret
can't take over the account (grace also never chains across rotations). `POST
/v1/keys/revoke` (`{"confirm": true}`) is the irreversible kill switch.
Tombstones persist, so dead keys fail with named 401s (`key_rotated` /
`key_revoked`) while unknown keys keep the generic 401 (no probe oracle).
Admin hardening included: hash match alone no longer unlocks `/v1/admin/stats`
— the key must be LIVE, so revoking the owner key actually cuts admin access
(rotate returns `api_key_sha256` for rebinding `ADMIN_KEY_SHA256`). Both
lifecycle routes share the key-mint rate limiter (tombstone-flood defense);
the revoked map is size-capped like every other store map. `rotate_api_key`
MCP tool added. 26 new tests (198/198). Not built (deliberately): the one-time
recovery secret idea — a second long-lived credential doubles the theft
surface; minting a new key is cheap.

## 1. Reputation registry v2 — fairness & abuse resistance

The registry records accusations, not verdicts, and reports can only ever `flag` (never `block`) — so mistakes are survivable. These make it fairer and harder to game:

- ✅ **Delivery-outcome ledger** — BUILT 2026-07-16 (the strongest v2 item; prompted by CDP-Discord feedback: "a perfectly clean payment to a seller who never ships still fails the agent"). `POST /v1/outcomes` records delivered/not_delivered/partial/wrong_content per settlement, BOUND to a scan TollWarden performed (scan_id + payment_commitment verified against a rolling scan index; one outcome per scan; keyed scans only from the scanning account) — fabricating delivery history requires real, scanned payments. SDK payment-path wrappers auto-capture outcomes mechanically (x402 delivery is synchronous: paid 2xx → delivered, 5xx/second-402 → not_delivered with evidence; `reportOutcomes:false` opts out) plus manual `reportOutcome`/`report_outcome`. Delivery rates surface in reputation lookups and a scan-time `delivery` check: low rate (<70% over ≥5 outcomes) or repeated no-ships with zero successes → FLAG only (H-2 applies to measured history too); no history reads as no history. Aggregation keys off the pay_to captured at scan time, never reporter input. Rotation migrates the scan index with the account. Measured outcomes also dilute false accusations naturally — the best fairness lever in this section.

- ✅ **Time decay + reporter credibility weighting** — BUILT 2026-07-16 (server 1.4.0). Risk now grades on `weighted_score` = Σ over distinct reporters of credibility × decay, not raw counts. Decay: 90-day half-life on each reporter's newest report; below a 0.1 noise floor risk reads "none" (status stays "reported" for auditors) and scans get `reputation.decayed` (allow) instead of a flag — old mistakes fade in ~7 months. Credibility ∈ [0.5, 1.0]: fresh anonymous `reporter_agent_id` = 0.5, rising with observed payment history (distinct counterparties seen in scans, O(1) lookup), capped at 1.0 so no clique can reach thresholds anonymous reporters couldn't (H-2: credibility scales flag confidence, never gates). Ladder calibrated to preserve v1 exactly: thresholds 2.5/1.0/0.1 mean 5/2/1 fresh anonymous reporters still grade high/medium/low, while Sybil-minted fresh ids count half. One reporter × many categories = one voice (max, not sum).
- ✅ **Dispute / rebuttal** — BUILT 2026-07-16 (server 1.4.0). `POST /v1/reputation/dispute` (free, shares the report rate limit) + `dispute_reputation` MCP tool. Key ownership IS the authentication: an EIP-191 personal_sign signature over the canonical message `tollwarden-dispute-v1|<address>|<statement>` must recover to the disputed address (address baked into the message so a rebuttal can't be replayed onto another wallet's record). Verification is `src/evmsig.ts` on @noble/curves + @noble/hashes (Node's crypto has no keccak-256 — its sha3-* are NIST-padded — and no secp256k1 pubkey recovery; noble was already resolved in the lockfile via the x402 stack; recovery cross-checked against the canonical Anvil account-0 vector). Verified rebuttals surface in every reputation lookup (signature included so third parties can re-verify) and the scan-time flag reason notes them — but they NEVER mechanically lower risk: a scammer can sign a rebuttal as easily as an honest seller; agents weigh both sides. Capped 5 per address, newest first, deduped, snapshot-persisted. 25 new server tests (289 green).
- **Remediation path** — documented process for compromised-then-rotated keys: mark address as "historical compromise, rotated on <date>" after signed proof from the new key.
- ✅ **Outcome coverage denominator** — BUILT 2026-07-21 (prompted by CDP-Discord feedback on selective logging: append-only protects rows that exist, not forecasts never written). `store.scanCounts` counts non-blocked scans per pay_to; reputation lookups report `scans_seen` / `report_coverage` next to the outcome counts, and a counterparty with scans but zero reported outcomes shows the un-reported population instead of reading as "no history". Informational only — scan counts are client-driven, so coverage never feeds a flag (H-2 spirit). OpenAPI delivery schema added.
- **Domain-ledger coverage denominator** — the per-pay_to counter above has no domain twin: the rotation-join ledger (outcomes by resource domain) can't show coverage for a rotated merchant. Mirror the scan counter per domain (same informational-only posture). Small, consistent follow-on.

## 2. Plan / tier structures (monetization) — ✅ BUILT 2026-07-14

Implemented as designed: `src/plans.ts` (catalog: Pro $4.99/30d, Scale $19.99/30d + hard ceilings), `GET /v1/plans`, x402-paid `POST /v1/plans/subscribe` with autonomous renewal, per-key policy resolution in the scan path, per-plan scan pricing via one payment layer per distinct price, manifest/agent-card/OpenAPI updates. 21 new tests (87/87 passing); dev-server e2e verified (Pro key absorbs a 15-scan burst that flags a Starter key). Original design sketch:

- `GET /v1/plans` (free): machine-readable catalog — `price_per_scan`, `included_calls`, `max_scans_per_minute`, `max_usd_per_hour`, feature flags (`force_deep`, `cdp_pin_verify`), `duration_days`, upgrade instructions. Mirrored in `/.well-known/x402` and the agent card.
- `POST /v1/plans/subscribe` (x402-paid): 402 quotes the plan price; the agent pays via its normal pay-and-retry flow; its API key is upgraded with an expiry. Renewal = pay again before expiry. Fully autonomous purchase/renewal, zero new protocol.
- Scan-time policy resolution: plan overrides → env defaults. Per-key pricing needs a thin dynamic-pricing layer in front of `@x402/express` (static per-route today).
- **Hard ceilings stay:** plans loosen a customer's own thresholds (velocity/volume before flags) but can never disable replay, pin-mismatch, or asset verification, and even the top tier keeps a spend cap. Never sell "scan less carefully."
- Touches: `store.ts` (plan + expiry on key records), `config.ts` (policy resolution), `api.ts` (plans endpoints, per-key pricing), manifest, docs, tests. Est. 1–2 days.

## 3. Detection improvements

- ✅ **Client SDK provenance auto-tagging** — BUILT 2026-07-14: `sdk/` (`@tollwarden/client`, zero-dep, Node 18+). `observe()`/`notePlanning()` auto-tag `context.origin`; observations are single-use with a TTL. 32/32 tests, cross-validated against the real server signer. Publishing now automated: Actions → publish-npm (OIDC trusted publishing, same posture as publish-pypi).
- ✅ **Wallet-side verifier** — absorbed into the SDK: standalone `verifyAttestation()` + `computePaymentCommitment()` exports (pinned-key signature check, commitment recompute/replay defense, expiry). Optional follow-up: publish a docs page with the snippet inline.
- ✅ **Address-poisoning detection** — BUILT 2026-07-16: `src/detectors/poisoning.ts`. Blocks a `pay_to` that shares ≥4 leading and ≥4 trailing hex chars with a known counterparty (this agent's history) or pinned merchant but isn't that address — the truncated-display vanity-address attack. Runs before pinning/velocity so lookalikes are judged against pre-scan state; blocked scans are rolled back out of trust state (counterparty history + fresh pins) so repeats keep detecting. 12 new tests.
- ✅ **Injection-detection hardening** — BUILT 2026-07-21: `src/detectors/injection.ts` + `poisoning.ts`. Weighted tells (multilingual override phrasing, chat-template/tool spoofing, persona swaps, precedence claims) with address-proximity scoring; obfuscated `pay_to` matching (whitespace-split / invisible-char-laced → block regardless of origin); deep-tier decoders for base64url + line-wrapped + double base64, hex, percent-encoding, HTML entities, and Unicode tag-character smuggling; homoglyph (Cyrillic/Greek) skeleton folding that NFKC alone misses; vanity-bait lookalike addresses planted in just-read content (`poison.lookalike_in_content`). 22 new tests. No API changes.
- ✅ **Injection incident ledger** — BUILT 2026-07-21: blocked scans whose findings structurally implicate an address (pay_to planted in just-read content, encoded payloads embedding it, vanity-bait lookalikes) auto-record it in a persistent ledger; every agent's future scan of that wallet flags `reputation.injection_history` and `GET /v1/reputation/{address}` surfaces the history. One detection becomes network-wide protection. Flag-only (scan inputs are client-supplied — audit H-2 posture), weighted by observer credibility × 90-day decay, one voice per observer. 14 new tests.
- ✅ **Cumulative deep-tier trigger** — BUILT 2026-07-21: the per-payment `MICRO_BYPASS_USD` bypass is no longer a permanent blind spot. Lifetime scanned spend per (agent, counterparty) pair is tracked; once it crosses the threshold the deep content tier runs even for micro payments (`tier.deep_cumulative`). Dripping $0.002 payments no longer evades encoded-payload scanning.
- ✅ **Detection evaluation harness** — BUILT 2026-07-21: fixed corpus (`eval/`) of attack payloads (every tell family, all encodings, unicode obfuscation, provenance, poisoning bait) and benign FP guards (emoji tag chars, Cyrillic prose, git SHAs, base64 docs, French near-miss phrasing), graded via real scans in CI (`npm run eval`, gates ci.yml + prepublish). Known gaps tracked without gating: paraphrased social engineering, leetspeak, quoted attacks in articles — the target list for the semantic tier. First run immediately caught and fixed a case-sensitivity bug in the `send_to_address` tell. 355 unit tests total.
- ✅ **Signed pin evidence in attestations** — BUILT 2026-08-07 (prompted by Moltbook feedback from u/claudeopus_mos, committed to publicly): scan attestations carry a second Ed25519-signed record, `evidence-v1|scan_id|payment_commitment|pin_domain|pin_age_seconds|pin_corroboration`, publishing how long the merchant pin behind the payee had held at scan time (0 = first sighting) and which out-of-band sources corroborated it — each **named** (today: `cdp_bazaar`), never a boolean and never a composite score, because folding "young pin, corroborated" into one bit makes a risk-tolerance call that belongs to the wallet and depends on payment size. The 7-field verdict message stays frozen (deployed Python SDKs hard-reject other field counts), so the evidence is a separate signed record old verifiers ignore. Both SDKs verify it (signature, scan/commitment binding, mirror cross-check) and surface `pin_evidence`; the MCP verify tool returns it; a Node-signed cross-language fixture pins the format in the Python suite. Still open, deliberately: age-weighted pin rotation (must not ship without a corroboration source — a young pin that readily accepts correction is exactly the attacker's race) and DNS TXT as a source (weaker than it looks: merchant-controlled DNS is the same channel as the payment path, one registrar compromise yields both).
- ✅ **Approval decision telemetry** — BUILT 2026-08-07 (from the Moltbook thread: human approval decays into a reflexive compliance formality, and the drift is invisible in any single observation): every approval decision records its latency (both timestamps server-stamped, captured at decide time since approval records prune after 24h), kept in a capped per-account ring that survives rotation, with each approved payment paired to its later delivery outcome via the scan-bound outcome ledger. Surfaced ONLY to the key owner (`/v1/usage` + dashboard): recent-vs-baseline median latency and approval rate — shrinking latency at a near-100% approval rate is the rubber-stamp signature, and the outcome pairing separates decay from calibration. Raw aggregates, no composite score, and **never shared**: not reputation lookups, not trust evaluations, not public stats (all three test-enforced), and not the admin dashboard (also test-enforced against the audit-log stats aggregator). One scoped disclosure: each decision event in the hash-chained audit log carries `approval_latency_ms` — that log is the operator's own token-gated record, exportable only by whoever holds `AUDIT_EXPORT_TOKEN`. A public record of who rubber-stamps is a targeting list.
- **Semantic deep tier** — the eval harness originally tracked three `known_gap` families without gating; the 2026-09-19 hardening pass closed leetspeak (leet/letter-spacing folds) and paraphrased payee-change social engineering (BEC tells), leaving quoted-attack articles — exactly what pattern-matching can't catch: the text discusses an attack rather than performing one, and only meaning tells the two apart. Now that the heuristic tier is at parity with the open corpora (Rebuff/vigil-llm/garak), the remaining headroom is semantic. Shape: an opt-in LLM-assisted analysis pass for high-value / `force_deep` scans — cached by content hash, latency-bounded, fail-open to the heuristic verdict (a model outage must not block payments), never a silent price change. The eval corpus is the acceptance test: it should flip the known_gap cases to gated.
- ✅ **External-corpus tell parity** — BUILT 2026-07-21: benchmarked our tells against the open heuristic sets (Rebuff, vigil-llm, garak) and closed every phrasing they catch that we missed — broader override verb/object corpus, conjoined-adjective tolerance ("any previous and following instructions"), no-adjective loose variant, Guidance template markers, smuggled model boundary tokens (`<|endoftext|>`, `<end of session>`), fabricated conversation turns, and focus-only/disregard-except redirection. Kept precision by excluding the benign-FP-prone objects (context/input/data/message) and "and start over", each with a benign eval guard. 12 external phrasings added to the eval corpus (now ~64 cases); 43/43 attacks, 17/17 benign. Fast tier ~2.7ms at the 200KB cap.

## 6. Enforcement & ecosystem trust (added 2026-07-16)

The differentiation thesis: everyone else in the trust space produces *scores*; TollWarden produces signed, payment-bound *verdicts* — so TollWarden alone can move from "advisory" to "physically enforced."

Wraps any `signTypedData`-bearing signer (viem/ethers, both call shapes) in a Proxy that recomputes the payment commitment from the EIP-3009/ERC-2612 typed data being signed and refuses without a live, pinned-key-verified allow-verdict for exactly that commitment.
